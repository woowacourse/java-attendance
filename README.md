## 사용 방법

### 출석 규칙

- 시간은 24시간 형식만 사용한다. 예를 들어, "22:30"은 오후 10시 30분을 의미한다.
- 월요일은 13:00~18:00, 화요일~금요일은 10:00~18:00이다.
- 해당 요일의 시작 시각으로부터 5분 초과는 지각으로 간주한다.
- 해당 요일의 시작 시각으로부터 30분 초과는 결석으로 간주한다.
- 등교하지 않아 출석 기록이 없는 날은 결석으로 간주한다.
- 누적 지각 및 결석 횟수에 따라 경고 또는 면담을 시행한다. 또한 결석 횟수가 5회를 초과할 때 제적을 시행한다.
- 지각 3회는 결석 1회로 간주한다.
- 경고 대상자: 결석 2회 이상
- 면담 대상자: 결석 3회 이상
- 제적 대상자: 결석 5회 초과
- 캠퍼스 운영 시간은 매일 08:00~23:00이다.
- 주말 및 공휴일에는 출석을 받지 않는다.

### 출석

닉네임과 등교 시간을 입력하면 출석할 수 있다.   
출석 후 출석 기록을 확인할 수 있다.    
이미 출석한 경우, 다시 출석할 수 없으며 수정 기능을 이용하도록 안내한다.

### 출석 수정

출석 확인을 수정하려면 닉네임, 수정하려는 날짜, 등교 시간을 입력하여 기록을 수정할 수 있다.   
수정 후에는 변경 전과 변경 후의 출석 기록을 확인할 수 있다.

### 출석 이력 확인

닉네임을 입력하면 전날까지의 크루 출석 기록을 확인할 수 있다.

### 제적 위험자

전날까지의 크루 출석 기록을 바탕으로 제적 위험자를 파악한다.   
제적 위험자는 제적 대상자, 면담 대상자, 경고 대상자순으로 출력한다    
대상 항목별 정렬 순서는 지각을 결석으로 간주하여 내림차순한다.    
출석 상태가 같으면 닉네임으로 오름차순 정렬한다.

# 📌 Step2 목표

## ✅ TDD를 제대로 적용하고 있는지 확인받기 위해 상세한 커밋 로그 추가

제가 생각하는 TDD는 다음과 같습니다.

- 테스트를 작성하고 실패하는지 확인
- 일단 빠르게 성공하게 구현
- 필요하다고 판단되면 리팩토링

이 과정을 통해 현재 하는 작업 하나하나에 집중하는 방식입니다.  
**TDD를 제대로 이해하고 있는지 아서와 함께 얘기해보면 좋을 것 같아요!**

## ✅ 테스트 커버리지 검토

저는 엄청나게 엄격하게 테스트를 만들지는 않지만,  
**"이 정도면 전체 기능을 커버하는 데 충분한가?"** 가 궁금합니다.

## ✅ 객체가 자신의 책임만 가지도록 구현

- 협력이 필요하다면 **의존성을 최소화**
- `Validation` 책임이 필요할 경우, **별도 객체로 분리**

## ✅ 변경 시 영향 범위를 최소화하는 설계

- 기능을 추가하거나 변경할 때 **수정해야 하는 객체가 최소화**되도록 설계

## ✅ Step1 피드백을 반영하여 최소한의 설계로 구현

- **SRP 원칙을 기반으로**, 도메인별 책임을 명확히 나누고  
  애플리케이션이 잘 동작하는 것이 목표

# ❓ 질문

## 🔹 TDD에서 ‘단위’란?

TDD를 진행하면서 ‘단위’라는 개념이 다르게 해석되는 경우가 있어 고민이 됩니다.

- 주변 크루들은 **단위를 가장 작은 요소**(예: Validation 로직)로 보는 경향이 있습니다.
- 저는 **단위라는 개념이 사람마다 다를 수 있다**고 생각하고,  
  **외부 모듈을 주입받아 사용하는 것이 아니라면, 핵심 기능(예: 출석 확인)도 단위가 될 수 있다**고 생각합니다.

이 부분에 대해 어떻게 생각하시나요?

## 🔹 유틸리티성 객체의 필요성?

도메인 비즈니스 로직을 처리하는 과정에서 **유틸리티성 객체를 왜 사용하는지 궁금합니다.**

- `static` 메서드를 오픈하면 여기저기서 쉽게 사용될 수 있지만,  
  항상 해당 유틸리티의 존재를 고려해야 해서 복잡도가 증가할 것 같습니다.
- **만약 주입받아서 사용한다면 책임이 명확해질 것 같은데**,  
  유틸리티 객체를 굳이 사용하는 이유가 무엇일까요?
- 혹시 **복잡도와 관련이 있는 것일까요?**
- 정말 여러 도메인에서 공통적으로 사용된다면 **유틸리티도 나쁜 선택은 아닐 것 같은데**,  
  이 이유가 맞을까요?

## 🔹 Depth(깊이)에 대한 고민

피드백에서 **Depth를 줄이라는 조언**을 받았습니다.  
이는 **계층 구조뿐만 아니라 객체 간의 관계 깊이도 포함된다고 이해**했습니다.

하지만 **SRP 원칙을 따르다 보면 객체가 세분화되면서 Depth가 깊어지는 문제**가 발생할 것 같습니다.

- 이것은 **트레이드오프일까요?**
- Depth를 줄이는 대신 **책임을 명확히 가져가야 하는 걸까요?**
- 아니면 **더 좋은 해결 방법이 있을까요?**

## 🔹 확장성을 고려한 설계 학습 방법

지금까지는 객체지향 설계에서 **SRP(단일 책임 원칙)와 역할 분배**에 집중했습니다.  
확장성은 **인터페이스를 활용하여 구현하는 정도**로 이해하고 있습니다.

혹시 **추가로 공부하면 좋을 키워드나 개념**이 있을까요?
