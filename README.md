# 비즈니스 룰

- 교육 시간은 월요일은 13:00-18:00, 화요일부터 금요일은 10:00-18:00이다.
    - 해당 요일의 시작 시각으로부터 5분 초과는 지각으로 간주한다.
    - 해당 요일의 시작 시각으로부터 30분 초과는 결석으로 간주한다.
- 캠퍼스 운영 시간은 매일 08:00~23:00이다.
- 주말 및 공휴일에는 출석을 받지 않는다.

- 프로그램은 사용자가 종료할 때까지 종료되지 않으며, 해당 기능을 수행한 후 초기 화면으로 돌아간다.
- 등교하지 않아 출석 기록이 없는 날은 결석으로 간주한다.
- 지각 3회는 결석 1회로 간주한다.
    - 경고 대상자: 결석 2회 이상
    - 면담 대상자: 결석 3회 이상
    - 제적 대상자: 결석 5회 초과

## 기능 요구사항

### 출석 확인

- 닉네임과 등교 시간을 입력하면 출석할 수 있다.
- 출석 후 출석 기록을 확인할 수 있다.
- 이미 출석한 경우, 다시 출석할 수 없으며 수정 기능을 이용하도록 안내한다.
- 출석 확인은 크루가 캠퍼스에 들어온 후, 시스템에 출석 데이터가 저장된 시간을 기준으로 한다.
- 시간은 24시간 형식만 사용한다. 예를 들어, "22:30"은 오후 10시 30분을 의미한다.

### 출석 수정

- 출석 확인을 수정하려면 닉네임, 수정하려는 날짜, 등교 시간을 입력하여 기록을 수정할 수 있다.
- 수정 후에는 변경 전과 변경 후의 출석 기록을 확인할 수 있다.

### 크루별 출석 기록 확인

- 닉네임을 입력하면 전날까지의 크루 출석 기록을 확인할 수 있다.

### 제적 위험자 확인

- 전날까지의 크루 출석 기록을 바탕으로 제적 위험자를 파악한다.
- 제적 위험자는 제적 대상자, 면담 대상자, 경고 대상자순으로 출력한다.
- 대상 항목별 정렬 순서는 지각을 결석으로 간주하여 내림차순한다.
- 출석 상태가 같으면 닉네임으로 오름차순 정렬한다.

### 1차 피드백에 대한 리펙터링 순서

1. 리펙토링은 step1 기반의 새로운 브랜치 step1-refactor에서 진행
2. 테스트 케이스 재작성
3. 계층 구조 제거 (리펙토링 없이 순수하게 제거한다.)
4. 단위 테스트 별 RED 케이스 코드를 작성
5. 이에 맞게 각 기능 구현을 통한 Test 케이스 통과
6. 세부 사항 리펙터링
7. 전체 기능에 대해 4~6단계 반복
8. 실행 가능한 서비스 구조가 되도록 리펙터링 진행
9. step1에 머지한 후 Push, 원본 레포지에 대한 PR 업데이트

이때 각 단계별로 commit을 함으로, TDD에 대한 학습 피드백을 받고자 합니다.
커밋 단위가 너무 세분화 되었음이 염려되기에, 4-5 번의 커밋은 함께 진행했습니다.
또한, TDD 학습이 주된 목표이기에, Test 코드 작성과 매칭되는 기능의 경우 refactor 대신 feat으로 커밋했습니다.(4-5번에 대한 커밋)

### 리펙터링 아쉬운점 : 객체의 기준

- StatusStatistic와 manager 객체들
  manager 객체들은 도메인 데이터에 대한 요청과 출력을 위한 데이터를 관리합니다.
  그러나, StatusStatistic 객체에서는 출력 형식에 대한 작업을 스스로 하는 점은 설계 상 오류라 느껴집니다.

  또한, Manager의 경우, 피드백에서 자료로 확인한 "다형성을 활용한 Switch/case 사용"을 시도하며 수정하였습니다.
  이때, "다형성을 활용한 Switch/case 사용"은 현재 도메인 객체를 대상으로 한다면, View의 영역이 도메인을 침범하는 일이 생겼습니다.
  때문에, 이 방법을 제거하는 리펙터링이 추가되었으며, 다소 초기 설계와 다른 구조로 넘어가 기준이 다소 모호해졌음을 느꼈습니다.

  이 문제들은 구조적인 문제이기에, TDD가 우선인 현 미션에서 후순위로 두었고, 2단계 미션에서 좀 더 발전시켜보고자 합니다.
